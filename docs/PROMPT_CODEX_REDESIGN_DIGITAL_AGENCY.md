# Задание для Codex: полная переработка сайта digital-агентства

## 0. Режим работы

Ты работаешь внутри существующего репозитория сайта:

- репозиторий: `MaximKudriavtsev/web-studio-landing`;
- текущий публичный адрес: `https://maximkudriavtsev.github.io/web-studio-landing/`;
- проект уже создан и запускается;
- текущий стек нужно сохранить, если нет действительно веской технической причины его менять.

Перед внесением изменений:

1. Полностью изучи структуру репозитория, текущие страницы, компоненты, стили, маршруты, `package.json`, `vite.config.ts`, скрипты сборки и файл контента.
2. Запусти проект локально и зафиксируй текущее состояние.
3. Изучи все приложенные изображения-референсы:
   - `01-homepage-reference.png`;
   - `02-services-reference.png`;
   - `03-cases-reference.png`;
   - `04-contact-reference.png`.
4. Используй референсы как основной ориентир по композиции, визуальному языку, плотности, типографике и иерархии.
5. Не копируй изображение пиксель-в-пиксель как одну картинку. Весь интерфейс должен быть собран нативно из HTML, React-компонентов, CSS/Tailwind, SVG и оптимизированных локальных изображений.
6. Работай автономно: не останавливайся после анализа и не проси подтверждение каждого этапа. Выполни полную переработку, затем проверь проект и выдай отчёт.

## 1. Главная цель

Полностью переработать существующий сайт веб-студии в современный, лёгкий, уверенный и коммерчески понятный сайт небольшого digital-агентства.

Сайт должен показывать, что команда:

- создаёт сайты и цифровые продукты для бизнеса;
- разрабатывает интернет-магазины;
- делает сайты для предпринимателей и продавцов маркетплейсов;
- проектирует веб-сервисы, кабинеты и внутренние системы;
- занимается UX/UI-дизайном, редизайном, развитием и сопровождением;
- понимает не только дизайн и код, но и реальные бизнес-процессы.

Основная коммерческая точка входа на первом этапе:

> Сайты и интернет-магазины для предпринимателей и продавцов маркетплейсов, в том числе проекты на Яндекс КИТ.

При этом агентство нельзя позиционировать исключительно как подрядчика по Яндекс КИТ. КИТ — отдельный заметный продукт внутри более широкого digital-предложения.

## 2. Исходный технический стек

Сохрани текущий стек проекта:

- Vite;
- React;
- TypeScript;
- React Router;
- Tailwind CSS;
- Motion / существующую библиотеку анимации;
- `lucide-react` для иконок;
- статическую сборку без обязательного собственного сервера.

Текущий проект поддерживает:

- GitHub Pages с `base: /web-studio-landing/`;
- сборку с корневым `base: /` для собственного домена или Object Storage;
- SPA-маршруты и `404.html`.

Не ломай эти сценарии.

Допускается:

- переработать структуру компонентов;
- расширить типы контента;
- создать новые reusable-компоненты;
- добавить небольшую зависимость, только если она действительно нужна и не дублирует имеющийся функционал.

Не допускается:

- переписывать проект на другой фреймворк;
- добавлять тяжёлую UI-библиотеку;
- использовать Bootstrap, Material UI или готовый шаблон;
- превращать проект в набор жёстко прошитых страниц без общей системы;
- хранить секреты, токены или ключи в клиентском коде.

## 4. Работа с названием бренда

Название бренда пока окончательно не утверждено.

В визуальных референсах используется `NOVA`, но это только временный визуальный плейсхолдер. Не размазывай название по компонентам и файлам.

Сделай единый источник:

```ts
site.brand.name
site.brand.descriptor
site.brand.shortName
```

Для текущей демонстрационной версии можно использовать:

```ts
name: 'NOVA',
descriptor: 'digital agency',
shortName: 'NOVA',
```

Но обязательно:

- добавь рядом комментарий `TODO: временное название, заменить до публикации`;
- сделай замену названия возможной в одном месте;
- не используй домен `nova-agency.ru`;
- не добавляй ложные реквизиты или фиктивную регистрацию бренда;
- favicon и логотип должны генерироваться из нейтрального знака/букв и также легко заменяться.

В README добавь отдельный пункт о том, где меняется бренд.

## 5. Общий визуальный стиль

Ориентируйся на приложенные изображения.

### Характер интерфейса

- светлый;
- современный;
- аккуратный;
- премиальный, но не пафосный;
- дружелюбный к предпринимателю;
- без чрезмерной «айтишности»;
- без неона, кислотных цветов, стекломорфизма на каждом блоке и перегруженных 3D-эффектов.

### Важное замечание по референсам

На референсах страницы показаны внутри рамки браузера. Эта рамка — только способ презентации макета.

**Не добавляй рамку браузера, адресную строку, красную/жёлтую/зелёную кнопки или внешний серый фон внутрь реального сайта.**

Реальный сайт начинается с Header и занимает обычное окно браузера.

### Базовые токены

Создай централизованные CSS-переменные или Tailwind-токены. Можно использовать близкие значения, уточнив их по визуалу:

```css
--page-bg: #fbfbfd;
--surface: #ffffff;
--surface-soft: #f6f7fb;
--text-primary: #111827;
--text-secondary: #667085;
--border: rgba(92, 94, 122, 0.14);
--accent: #5b5cf0;
--accent-strong: #4b4ce3;
--accent-soft: #eef0ff;
--success: #22a06b;
--shadow-sm: 0 10px 30px rgba(35, 38, 70, 0.06);
--shadow-md: 0 20px 60px rgba(35, 38, 70, 0.10);
--radius-sm: 12px;
--radius-md: 18px;
--radius-lg: 26px;
--container: 1200px;
```

Не воспринимай значения как обязательные до пикселя. Важнее визуальная цель.

### Типографика

Используй современный гротеск с хорошей кириллицей.

Предпочтительно:

- `Manrope`, `Inter`, `Onest` или системный fallback;
- шрифт должен подключаться безопасно;
- не блокируй отображение страницы из-за внешнего CDN;
- предпочтительно положить webfont в проект или использовать устойчивый системный стек;
- не добавляй файлы шрифтов без корректной лицензии.

Иерархия:

- H1 desktop: примерно 56–68 px, плотный line-height;
- H1 mobile: примерно 36–44 px;
- H2 desktop: 36–46 px;
- основной текст: 16–18 px;
- мелкие подписи: не меньше 13–14 px;
- строки не должны быть чрезмерно длинными.

### Сетка и отступы

- максимальная ширина контента: 1160–1240 px;
- крупные вертикальные отступы между секциями;
- на desktop использовать 12-колоночную логику;
- на tablet и mobile перестраивать без горизонтального скролла;
- карточки должны иметь согласованные padding, border-radius и высоту;
- не пытайся уместить все desktop-блоки в одну строку на мобильном.

### Визуальные эффекты

Разрешено:

- мягкие градиентные свечения;
- тонкие рамки;
- деликатные тени;
- лёгкое движение декоративных элементов;
- hover-подъём карточки на 2–4 px;
- плавное появление секций.

Запрещено:

- чрезмерное мерцание;
- тяжёлый parallax;
- анимация текста, мешающая чтению;
- постоянное движение всех элементов;
- обязательная анимация для понимания интерфейса.

Учитывай `prefers-reduced-motion`.

## 6. Архитектура сайта и маршруты

Должны быть реализованы четыре полноценные страницы:

```txt
/           Главная
/services   Услуги
/work       Кейсы
/contact    Контакты
```

Пункт `Процесс` в шапке ведёт на секцию `/#process`.

На внутренних страницах клик по `Процесс` должен:

1. перейти на главную;
2. корректно проскроллить к секции `#process`;
3. учитывать sticky-header;
4. не ломаться на GitHub Pages с нестандартным `base`.

Добавь:

- страницу 404 или корректный fallback;
- прокрутку наверх при переходе между страницами;
- восстановление фокуса/доступность маршрутизации;
- активное состояние текущего пункта меню.

- нет `any` без реальной необходимости.

## 8. Header

Header должен соответствовать визуальному референсу.

### Desktop

Слева:

- текстовый логотип;
- название крупнее;
- descriptor `digital agency` мелко под ним.

По центру/справа:

- `Главная`;
- `Услуги`;
- `Кейсы`;
- `Процесс`;
- `Контакты`;
- CTA `Обсудить проект`.

Поведение:

- sticky после начала прокрутки;
- полупрозрачный светлый фон с blur допустим, но без снижения читаемости;
- активный пункт подчёркивается акцентной линией;
- CTA ведёт на `/contact`;
- высота компактная;
- не перекрывает контент.

### Mobile

- логотип слева;
- кнопка меню справа;
- доступное раскрывающееся меню;
- закрытие по Escape, клику по ссылке и клику вне меню;
- блокировка фонового скролла;
- корректные `aria-expanded`, `aria-controls`, фокус и tab-order;
- CTA внутри меню.

# 19. Персональные данные, cookie и аналитика

Поскольку на сайте есть форма, подготовь юридически корректную техническую основу, но не придумывай содержание за владельца.

## Форма

До отправки обязательно:

- явное согласие;
- ссылка на политику;
- ссылка на согласие на обработку ПД;
- без заранее установленной галочки.

## Cookie

Если никакая аналитика не подключена:

- не показывай бессмысленный cookie-баннер;
- оставь компонент/механику готовыми к включению.

Если задан:

```env
VITE_YANDEX_METRICA_ID=
```

то:

- не загружай Метрику до согласия на аналитические cookie;
- добавь `Принять`, `Отклонить`, `Настроить`;
- отказ должен быть таким же доступным, как согласие;
- хранить выбор пользователя;
- дать возможность открыть настройки из Footer;
- не включать вебвизор и дополнительные функции автоматически без явной конфигурации.

Не подключай внешние трекеры по умолчанию.

# 20. Производительность

Цели:

- быстрый первый экран;
- минимальный layout shift;
- отсутствие тяжёлых библиотек ради простых эффектов;
- оптимизированные изображения;
- разумное code splitting по страницам;
- lazy-load внутренних страниц при возможности;
- не загружать все case-изображения на первом экране;
- не использовать огромные blur-изображения;
- SVG-иконки вместо PNG там, где уместно.

Ориентир Lighthouse, без попытки «накрутить» результат:

- Performance ≥ 90;
- Accessibility ≥ 95;
- Best Practices ≥ 95;
- SEO ≥ 95.

Если локальный результат ниже, укажи причины и исправь всё, что возможно в рамках проекта.

- README обновлён;
- юридическая и cookie-основа подготовлена без фиктивных реквизитов;
